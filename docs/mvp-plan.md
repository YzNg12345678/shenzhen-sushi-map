# 深圳寿司地图 MVP 方案

## 1. 产品目标

做一个个人自用的深圳寿司决策与记录网站。它不追求覆盖所有餐厅，而是帮助用户：

1. 按真实用餐场景快速选出 3 家候选店。
2. 用寿司专业维度比较店铺，而不是看综合五星。
3. 记录吃过的店、鱼种和每一贯的评价，形成个人口味画像。
4. 知道当前季节值得吃什么鱼，并关联到可能提供的店铺。

## 2. 第一版范围

### 页面

- `/`：深圳寿司地图与筛选。
- `/choose`：按场景选店，一次只返回 3 家并解释取舍。
- `/shops/[slug]`：店铺详情、来源证据、专业标签、个人记录。
- `/passport`：个人寿司护照、打卡历史、口味画像。
- `/season`：约 40 种鱼的季节日历。
- `/compare`：最多 3 家横向比较。

### 场景

- 一人吃
- 约会
- 请客
- 深夜
- 初次 omakase
- 指定预算

### 店铺核心字段

- 基础：名称、地址、经纬度、区域、营业时间、人均、预约方式、来源链接。
- 专业：流派、赤酢/白酢、熟成倾向、师傅、吧台/桌席、套餐形式、可点单方式。
- 场景：一人友好、约会、商务、深夜、交通便利、预约难度。
- 证据：字段来源、抓取时间、置信度、人工确认状态。
- 个人：是否去过、日期、套餐、每贯记录、总评、复访意愿、私人备注。

## 3. 推荐逻辑

- 先用预算、营业状态、时间、预约可行性等硬条件排除。
- 再按场景权重计算确定性分数。
- 每个维度保留原始值、标准化值、权重和贡献，结果可解释。
- AI 不生成排名数字，只负责从笔记提取候选字段、归纳证据和生成自然语言解释。
- 推荐页只展示 3 家：最匹配、最稳妥、最有特色，避免变成另一个列表平台。

## 4. 数据方案

### 初始数据

- 目标：深圳 30–50 家店。
- 店铺基础信息以高德 Web 服务 API 补全。
- 小红书只提取事实字段和原链接，不转载正文或图片。
- 鱼种季节表先做人工维护的约 40 种静态数据。

### 提取管道

1. 读取现有 spider-xhs 的已授权采集产物。
2. 用 Zod/JSON Schema 定义 `ShopCandidate`。
3. Provider 接口支持 MiniMax 与 Mock；模型输出必须通过 Schema。
4. 校验失败自动纠错重试一次；仍失败进入人工队列。
5. 固定抽检 20%，记录字段准确率和来源可追溯率。
6. 人工确认后生成运行时 `shops.json`；原始材料不进入网站包。

## 5. 技术方案

- Web：Next.js App Router + TypeScript + Tailwind。
- 数据：版本化 JSON；个人记录放浏览器 localStorage，并提供 JSON 导入/导出备份。
- 地图：高德 JS API；Key 与安全密钥通过环境变量注入。
- 校验：Zod。
- 测试：Vitest + Testing Library + Playwright。
- 部署：第一阶段仅本机运行；结构保留后续 Vercel/Cloudflare Pages 发布能力。
- 首版无登录、无后端、无数据库、无社区、无评论、无付费排序。

## 6. 实施顺序与验收

### M0：干净骨架

- 初始化 Next.js、质量脚本、示例数据和 Schema。
- 验收：安装、lint、typecheck、unit test、build 全通过。

### M1：店铺地图与详情

- 录入 10 家人工确认样本，完成地图、筛选、详情和来源证据。
- 验收：深圳定位正确；筛选结果与数据一致；移动端浏览正常。

### M2：场景推荐与比较

- 完成硬过滤、可解释评分、3 家推荐和横向比较。
- 验收：固定黄金用例输出稳定，分数能逐项追溯。

### M3：寿司护照与季节日历

- 完成打卡、按贯记录、口味画像、鱼种日历、导入导出。
- 验收：刷新后数据仍在；备份导出后可完整恢复。

### M4：数据提取管道

- 接入现有小红书产物和高德补全，完成 Schema 校验与 20% 抽检。
- 验收：30–50 家店均有原始来源；核心字段抽检准确率达到约定阈值后才替换人工样本。

## 7. 暂不做

- 微信小程序、公开发布、账号体系、多人协作、评论社区、预约代订。
- 复杂后端、PostgreSQL、Redis、队列和对象存储。
- 师傅谱系自动推断；先保留字段，待证据足够再展示。

## 8. 开工前只需确认

- 项目名是否保留“深圳寿司地图”。
- 地图首屏是否以“店铺地图”为主，还是以“今天怎么吃”的场景问答为主。
